# Database model

This is the approved SQLite model for the MVP. Phase 5 implements the persistence API; Phase 6 connects the frontend to it.

The authoritative table definitions and constraints are in [database-schema.json](database-schema.json).

## Relationships

- A user owns one board in the MVP. The unique `boards.user_id` constraint enforces this while keeping data separated by user.
- A board owns ordered `board_columns` rows.
- Each card belongs to exactly one column. Its column and position determine where it appears on the board.
- Deleting a user, board, or column cascades to its owned data. Moving a card updates its `column_id` and position within a transaction.
- AI conversation history is intentionally deferred; it can be added as a separate table when persisted chat history is in scope.

## Frontend mapping

The database is normalized, while the current frontend uses `BoardData` with a list of columns and a card map. The API will read columns ordered by `position`, read their cards in position order, and assemble the existing shape:

```json
{
  "columns": [
    { "id": "column-id", "title": "Backlog", "cardIds": ["card-id"] }
  ],
  "cards": {
    "card-id": { "id": "card-id", "title": "Example", "details": "Card notes" }
  }
}
```

This keeps the frontend contract intact while avoiding duplicated card data in the database.

## Data flow

1. On first startup, the backend creates the SQLite tables, enables foreign keys, and seeds the demo user, one board, and the existing default columns and cards if they are absent.
2. The sign-in API validates the submitted username and password against the stored password hash and returns a bearer token. The plaintext demo password is never stored.
3. The frontend requests the signed-in user's board. The backend reads the user's board, columns, and cards and maps them to the existing `BoardData` response.
4. Board changes are sent to backend endpoints. Card movement and ordering changes are committed together so the stored positions stay consistent.

## Design boundaries

- Bearer-token sessions are held in backend memory and cleared when the service restarts. Persisted authentication sessions and AI chat history are outside this MVP phase.
- The one-board-per-user rule matches the MVP. Supporting multiple boards later requires removing one uniqueness constraint and adding board selection to the UI/API.
- IDs are generated by the backend as UUID strings. Timestamps are stored as UTC text.
